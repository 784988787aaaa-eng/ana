A. MISSION IDENTIFICATION

Objective:
Resolve AUDIT-DB-003 by determining whether customer_balances is authoritative, derived/cache, unused/dead schema, mixed/ambiguous, or unresolved from available evidence.

Primary conclusion:
The implementation evidence strongly establishes that customer_balances is NOT the runtime source of customer balances. Runtime customer-balance projections used by the customer UI are calculated directly from habayeb_transactions through HabayebDao.getAllCustomerBalancesFlow(). CustomerBalanceDao has no demonstrated production caller in the available source evidence. However, the repository's GitHub code-search index is disabled (repository metadata reports is_code_search_indexed=false), so a mechanically exhaustive whole-repository caller search cannot be certified. Therefore the final classification is UNRESOLVED rather than an overconfident UNUSED certification.

G. TRANSACTION-BOUNDARY ANALYSIS

customer_balances table:
- No production write transaction boundary was proven because no production writer was proven.
- The DAO itself contains no @Transaction mutation method.
- AppDatabase exposes the DAO but does not establish an aggregate mutation contract around it.

Active customer balance calculation:
- The balance used by the application is a read projection over habayeb_transactions.
- It is therefore automatically invalidated/recomputed by Room when the source query observes transaction-table changes.
- This is materially different from maintaining a separately persisted balance table.

No claim is made about runtime scheduling or actual Flow emissions beyond the static Room query contract.

H. AUTHORITY ANALYSIS

Candidate A — AUTHORITATIVE:
Not supported by inspected evidence. The customer UI does not read CustomerBalanceDao; it reads HabayebDao's transaction-derived projection.

Candidate B — DERIVED/CACHE:
Not supported as a current active persisted cache because no production write/read caller for CustomerBalanceDao was demonstrated. The actual active derived balance is CustomerCurrencyBalance, computed directly from habayeb_transactions.

Candidate C — UNUSED/DEAD SCHEMA:
Strongly supported by the implementation structure:
- entity is registered;
- DAO is exposed by AppDatabase;
- AppContainer does not inject/expose the DAO;
- active repositories use HabayebDao instead;
- UI/ViewModel uses HabayebRepository.customerBalancesFlow();
- BackupEngine omits the table;
- no production caller was found in inspected source.

But because whole-repository code search is unavailable, this cannot be elevated to PROVEN UNUSED for the entire repository.

Candidate D — MIXED/AMBIGUOUS:
No mixed runtime authority was demonstrated.

FINAL CLASSIFICATION:
UNRESOLVED
Reason: implementation strongly indicates UNUSED/DEAD SCHEMA, but complete whole-repository caller absence cannot be certified from the available evidence because code-search indexing is disabled.

BackupEngine.snapshot() reads and serializes:

customer_balances is absent.

BackupEngine.rootToDatabase() restores the same logical set and does not restore customer_balances.

Given the active runtime balance authority is habayeb_transactions-derived, omission of customer_balances from backup is consistent with the observed active runtime contract.

If a hidden production caller or external contract treats customer_balances as persisted user data, the omission would become a backup-completeness defect. That condition is not proven from available evidence.
